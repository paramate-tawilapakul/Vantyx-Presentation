Vantyx VNA architecture in detail

Vantyx คือ VNA/PACS แบบ self-hosted: modality หรือ PACS ของโรงพยาบาลส่ง DICOM เข้า Orthanc แล้ว event pipeline จะ index แต่ละ study ลง PostgreSQL ส่วน pixel data เก็บใน SeaweedFS S3 ผู้ใช้เปิดงานผ่าน web client และ DICOM viewer บน browser และ HIS เชื่อมด้วย HL7 v2 ทั้งระบบรันเป็น Docker Compose stack เดียว (25 services — ภาพนี้วาด 22 component แบ่งเป็น 4 โซน)

Clients & external

ผู้ใช้และระบบภายนอก: web client, DICOM viewer, HIS ของโรงพยาบาล และ modality / PACS

Web tier

ทางเข้าของ browser: edge (Cloudflare หรือ LAN) → nginx กระจายโหลดแบบ least_conn → JWT Auth → Fastify API ×3 พร้อม Redis, PostgreSQL และ Logs DB

Event pipeline

งาน async ผ่าน RabbitMQ: publisher รับ event, consumer index study, transcoder ทำวิดีโอ, HL7 Worker คุยกับ HIS และ cronjob ดูแลระบบ

Archive & backup

ที่เก็บภาพ: Orthanc + index DB, SeaweedFS (hot ssd / cold hdd) + filer DB และ pgBackRest ที่สำรอง 3 database

Deployเครื่องนี้เป็น dev/demo เปิดผ่าน Cloudflare tunnel · โรงพยาบาลใช้ VM เดียว (S1) หรือ HA 2 เครื่อง + witness (L1) ภายใน LAN ไม่ผ่าน Cloudflare

Entry points

ทางเข้า 3 ทาง

  • Browser → nginx :8090 (API + เว็บ) / :81 (viewer) → JWT Auth → Fastify API 3 replicas (least_conn) — ทางเข้า nginx มี 2 แบบตามที่ deploy:
  • Cloudflare tunnel (เครื่อง demo นี้ vna.ptvantyx.com) หรือ on-premise: browser ใน LAN โรงพยาบาลเข้า nginx ตรงด้วย static IP (VM แบบ S1 / L1 ไม่รัน cloudflared ถ้าใช้ http ธรรมดาต้องตั้ง COOKIE_SECURE=false)
  • HL7: HIS → MLLP :2575 เปิดตรงบน host ไม่ผ่าน nginx — HL7 Worker ตอบ ACK เอง แล้วเรียก API ด้วย x-api-key
  • DICOM: modality / PACS → Orthanc :4242 รับเฉพาะ AE ที่ลงทะเบียนใน Settings › DICOM Nodes

Auth

JWT Auth กับ session

  • access token 30 นาที (ส่งใน JSON body) + refresh token 3 วัน ใน httpOnly cookie ที่ใช้ได้เฉพาะ /api/v1/auth
  • session เก็บใน Redis refresh:<user>:<session> หมุน token ทุกครั้งที่ refresh และจับการใช้ token ซ้ำ ทุกครั้งที่ revoke จะเขียน denylist ไว้ด้วย
  • token มี permissions, แผนก และ AE-Title scope → authorize() + study-scope guard ถ้า study อยู่นอก scope จะตอบ 404
  • รูปภาพและ DICOMweb ก็ตรวจ token เหมือนกัน (IMAGE_AUTH_MODE=enforce + nginx auth_request)

Image delivery

ภาพไปถึง viewer

  • viewer ขอภาพแบบ WADO-RS ผ่าน API proxy (/dicom-web/*, GET only + allow-list) → Orthanc ด้วย Basic auth — Cornerstone beforeSend refresh token ก่อนส่ง และดึงพร้อมกันได้ 24 ภาพ
  • nginx proxy_cache (named volume) ตรวจ token ด้วย auth_request (cache ผล 60 วินาที) แล้วตอบ frame จาก cache — cache HIT ไม่ถึง Node และ Orthanc
  • Orthanc เก็บแบบ JPEG-LS lossless ตั้งแต่ ingest (เครื่องนี้ 21.3 → 7.1 GB)
  • multi-frame เช่น US cine โหลดทั้งไฟล์ครั้งเดียวแบบ wadouri: ไม่ดึงทีละ frame — ประวัติผู้ป่วยโหลดแบบ light (ดึง instance ของ series เมื่อเปิดดู)
  • DICOM video → worker-transcoder ทำ MP4 เก็บใน video-cache · มือถือ/แท็บเล็ตใช้ภาพ /rendered JPEG แบบ 1×1

HL7 v2

เชื่อมต่อ HIS

  • HIS ส่ง ADT/ORM ทาง MLLP :2575 → HL7 Worker ตอบ ACK แล้วส่งต่อเข้าคิว RabbitMQ hl7.inbound
  • consumer ในตัว HL7 Worker เรียก POST /api/v1/hl7/inbound ด้วย x-api-key — business logic อยู่ใน server/src/modules/hl7/
  • เมื่อมี study ใหม่ worker-consumer ส่งเข้า hl7.outbound → HL7 Worker ส่ง ORU^R01 “images available” กลับไปที่ HIS (ไม่แนบ URL)
  • HIS เปิดภาพผ่าน Viewer Launch API: ได้ token ใช้ครั้งเดียว แลกเป็น session ของ integration user

Event pipeline

RabbitMQ และ workers

  • Orthanc Lua ยิง webhook เมื่อ study stable → worker-publisher → คิว quorum (x-delivery-limit 5 + DLQ)
  • worker-consumer: ดึงรายละเอียดจาก Orthanc → EMPI → upsert studies → ลบ Redis key ระดับผู้ป่วย → system_logs → ส่ง hl7.outbound เมื่อเป็น study ใหม่
  • worker-transcoder: วิดีโอใน staging/ → MP4 และ DICOM video → bucket video-cache
  • worker-cronjob (เที่ยงคืน + ทุก 5 นาที): prune, monitor, reconcile Orthanc /changes, tier SeaweedFS hot → cold, sync DICOM Nodes

Storage & backup

ข้อมูลและการสำรอง

  • PostgreSQL 18 ×4: vantyx, logs, Orthanc index, filer — pgBackRest สำรอง 3 ตัว (WAL + full รายสัปดาห์ + diff รายวัน → D:/db_backup)
  • postgres-logs และไฟล์ DICOM ไม่ได้ backup
  • SeaweedFS buckets: dicom · non-dicom · other-files · video-cache — replication 000 บนเครื่องนี้ (S1 = 001, L1 = 010)
  • ไม่ได้วาด: Portainer, seaweed-init-buckets, container static ของ frontend/viewer, API → SeaweedFS (ไฟล์ non-DICOM), consumer → Redis
