สูงS–M
คืออะไร
ข้อความสำเร็จรูปสั้น ๆ ที่แทรกตรงตำแหน่ง cursor ระหว่างพิมพ์ผล — ต่างจาก template ที่เป็นรายงานทั้งฉบับและใช้ตอนเริ่ม; macro ใช้ได้หลายครั้งในรายงานเดียวและผสมกันได้

  • กด Ctrl+Space เพื่อค้น macro จาก list เมื่อจำรหัสไม่ได้
  • macro มีช่องให้กรอก [ ] กด Tab กระโดดไปช่องถัดไป เช่น ขนาด, วันที่, ตำแหน่ง

ตอนนี้
มีแต่ template ทั้งฉบับ — ไม่พบ macro / autotext / dictionary ใน client; ทางเลือกตอนนี้คือ copy-paste หรือใช้ template ทั้งอันแล้วลบส่วนที่ไม่ใช้

1.6

SLA (Service Level Agreement) / TAT (Turnaround Time) alert เชิงรุก + dashboard จอใหญ่

สูงM
ปัญหา
time guarantee ตอนนี้ทำงานแค่บนหน้าจอของคนที่เปิด list อยู่ (สีกระพริบ) — ถ้าไม่มีใครเปิดดู เคสเกินเวลาก็ไม่มีใครรู้ และหัวหน้าไม่มีภาพรวมแบบ real-time
ส่วนที่ 1: Alert job
job ฝั่ง server ทุก 1–5 นาที หาเคสที่ยังไม่ sign แล้วเทียบเวลารอกับ time guarantee ของ modality + priority
  • ใกล้ถึงเวลา (เช่น 80%) → แจ้งรังสีแพทย์ที่ถูก assign
  • เกินเวลา → แจ้งหัวหน้าเวร / หัวหน้าแผนก
  • ยังไม่มีคน assign → แจ้งผู้ทำหน้าที่ assign
  • แจ้งครั้งเดียวต่อเคสต่อระดับ ไม่ spam; ส่งผ่าน socket + notification ของข้อ 1.2
ส่วนที่ 2: Dashboard
  • backlog ต่อ modality: รอ assign / รออ่าน / draft
  • STAT ที่ยังไม่ sign พร้อมเวลาที่รอ
  • เคสที่ใกล้เกินเวลา เรียงตามเวลาที่เหลือ
  • median / P90 TAT วันนี้ เทียบค่าเฉลี่ย 7 วัน
  • งานค้างต่อรังสีแพทย์ (ต่อยอดหน้า Workload)
  • โหมดเต็มจอ refresh เอง สำหรับเปิดค้างบนจอในห้องอ่านผล / ห้องเทคนิค
ต่างจากที่มี
Statistics (iframe ไป STAT_SERVER) เป็นรายงานย้อนหลัง; TimeAlert.tsx กระพริบเฉพาะคนที่เปิด list; server/src/jobs/scheduler.ts มีแค่งาน cleanup ตอนเที่ยงคืน
ข้อมูล
timestamp ครบใน RIS_PERFORMANCE และ RIS_MODALITY.MD_TIME_*

2. ใช้ Ollama Local AI (ไม่เกี่ยวกับงานวินิจฉัย)

หลักการ

  • AI ไม่อ่านภาพทางการแพทย์ และไม่เสนอ finding / impression / severity
  • output เป็นข้อเสนอ ผู้ใช้ต้องกดยืนยันทุกครั้ง; เก็บ log ว่า AI เสนออะไรและผู้ใช้รับหรือไม่
  • server เป็นฝ่ายเรียก Ollama HTTP API (browser ไม่เรียกตรง) และใช้ format (JSON schema) เพื่อให้ได้ structured output
  • ทุก feature ต้องทำงานต่อได้เมื่อ Ollama ล่มหรือช้า (timeout → ซ่อนปุ่ม / ข้ามขั้น)
  • จุดขาย: ข้อมูลผู้ป่วยไม่ออกนอกโรงพยาบาล (PDPA) ต่างจากระบบที่ใช้ cloud AI
  • model: ทดสอบ LLM ที่เก่งภาษาไทย เช่น Typhoon / Qwen / Gemma และ embedding ที่รองรับภาษาไทย เช่น bge-m3; ใช้เครื่อง GPU แยกจาก DB server

2.6

Semantic search (ค้นตามความหมาย)

กลางM
ปัญหาตอนนี้
Report Search ค้นแบบ keyword (Match Phrase / AND / OR) — ต้องพิมพ์คำให้ตรงกับที่อยู่ในรายงาน แต่เรื่องเดียวกันเขียนได้หลายแบบ: ตัวย่อ, ไทยปนอังกฤษ, คำพ้อง, สะกดต่างกัน เช่น "pleural effusion" / "effusion" / "น้ำในช่องเยื่อหุ้มปอด" → เคสที่ต้องการบางส่วนหาไม่เจอ
ทำอย่างไร
  • แปลงข้อความรายงานที่ sign แล้วเป็น vector (embedding) ด้วย model ที่รองรับภาษาไทย เช่น bge-m3 ผ่าน Ollama
  • แปลงคำค้นเป็น vector แล้วหารายงานที่ความหมายใกล้กัน แม้ใช้คำต่างกัน
  • ใช้แบบ hybrid: รวมคะแนน keyword เดิม + semantic → ผลที่ตรงคำขึ้นก่อน ตามด้วยผลที่ความหมายใกล้
  • เพิ่มปุ่ม "หาเคสที่ข้อความคล้ายกัน" จากรายงานที่เปิดอยู่
ตัวอย่าง
อาจารย์หาเคสสอน "ก้อนที่ตับมีหินปูน" แล้วเจอทั้งรายงานที่เขียน "hepatic mass with calcification" และ "calcified liver lesion" → เพิ่มเข้า Teaching Files ได้ทันที; ใช้หากลุ่มเคสสำหรับงานวิจัยได้ด้วย
Implementation
ทำ embedding รายงานเก่าครั้งเดียวแบบ batch แล้วทำเพิ่มทุกครั้งที่ sign (ต่อจาก sendToReportSearch ที่ส่งรายงานไป search server อยู่แล้ว); เก็บ vector ใน Elasticsearch ที่รองรับอยู่แล้ว (v7.2.12) ถ้าเป็นรุ่นที่มี vector search หรือใช้ vector store แยก
ขอบเขต
ค้นจากข้อความรายงานที่ sign แล้วเท่านั้น ไม่ดูภาพ ไม่เสนอการวินิจฉัย และใช้สิทธิ์การเข้าถึงเดิมของ Report Search
